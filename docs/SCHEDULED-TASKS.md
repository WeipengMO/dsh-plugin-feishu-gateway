# 定时任务：DSH 原生 Schedule 与飞书通知

从 **DSH Web → 飞书管理 → 定时任务** 管理周期运行的 Agent 任务。调度由 DSH 的原生 `ctx.schedule` 服务执行，Gateway 负责跨 Profile 管理命令和向已授权飞书聊天发送通知，**不另建一套 Cron 引擎**。

## 使用方法

1. 打开「定时任务」，确认页面显示原生 Schedule 可用；不可用时先检查 Gateway Profile 是否挂载 DSH 原生 Schedule 服务。
2. 点击新建任务，输入**任务标题、提示词、执行时间/重复规则和时区**。
3. 对一次性、间隔、每日、每周、每月或 Cron 规则，先预览未来触发时间，再保存。
4. 可为任务配置飞书通知目标；只允许机器人权限和群/成员策略允许的私聊或群聊。
5. 保存后到任务列表查看下一次运行时间、状态，可暂停、恢复、立即执行或删除。
6. 到「运行历史」查看真实执行结果；必要时去「运维与诊断」确认通知是否发送成功。

## 需要理解的几个状态

| 页面状态 | 含义 |
| --- | --- |
| 已保存 / 已安排 | DSH 原生定时任务定义存在，不代表已经执行 |
| 已排队 | 管理命令通过 Web 发往 Gateway，**不代表操作已成功** |
| 已完成 | 对应管理命令或一次任务运行已经结束；请核对是哪个对象 |
| 通知已发送 | 飞书消息投递成功，不等于任务本身一定成功 |
| 暂停 | 原生定时规则暂停，不是删除任务历史 |
| Session | DSH 保存的一段任务执行对话；删除任务定义不意味着自动清除历史 |

如果任务/模型执行失败，不能为了补发通知自动重放已可能产生外部副作用的工具调用。旧对话与保留期限见 [会话管理](SESSION-CENTER-UX.md)。

## 常见问题

- **页面提示 Schedule 不可用**：检查 Gateway 的 `ctx.schedule` 服务是否真正挂载，和 DSH 版本/相关插件兼容性。
- **保存后没看到执行结果**：管理命令可能仍是排队状态；查看命令结果与运行记录，不要重复创建导致重复任务。
- **执行成功但飞书没有消息**：检查通知目标白名单/群策略、Outbox 与发送重试；此类问题与 Agent 执行状态独立。
- **删除定时任务是否会释放空间？** 不会自动删除已有 DSH Session 历史，也不等于清理旧消息。

## 实现与安全边界

- Schedule 是 DSH Host 的原生能力；Gateway 通过受限跨 Profile 命令桥操作。
- 权限在 Web 端校验后，Gateway owner 仍会再次检查白名单、机器人和群策略。
- 定时任务使用 DSH 原生 Agent、模型和工具审批，飞书通知只传递执行结果，不绕开原生沙箱。
- 更新、暂停、运行和删除的结果以 Gateway 真正处理后的记录为准。
- 历史账本可含 Token、耗时、Session 引用和失败原因；缺失数据不能伪造为零。
